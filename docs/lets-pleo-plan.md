# 렛츠 플레오 개발 계획 및 완료 판정 기준

> **2026-11-15 범위 변경:** 사용자가 장시간 시험을 중단하고 짧은 데모를 우선하도록 요청했다. 현재 시연 목표는 **차량 주행 → 기록·보상 생성 → 모바일 재료 수령 → 가구 제작·배치 → 주민 진행**이다. 아래 51개 기준은 후속 제품 완성 기준으로 보존하며, 이번 데모 완료와 혼동하지 않는다. 시연 방법과 증거는 [데모 안내](demo-guide.md)에 기록한다.

## 1. 목표와 이번 작업의 완료선

**차량에서 모은 재료로 Android 모바일의 3D 마을을 꾸미는 게임을 개발한다.**

사용자는 정차 중 차량 앱에서 탐험을 시작한다. 이후 내비게이션 등 다른 화면을 사용해도 주행을 기록한다. 주행으로 획득한 보상은 같은 계정의 모바일 앱으로 전달되며, 제작·건물 배치·주민 초대·마을 성장에 사용한다.

이번 작업은 **사용자 개입 없이 컴퓨터에서 검증 가능한 제품 완성**을 목표로 한다.

- Pleos 에뮬레이터에서 차량 앱을 실행한다.
- Android 모바일 에뮬레이터에서 실제 모바일 APK를 실행한다.
- 컴퓨터에서 실제 서버와 영속 DB를 실행한다.
- 세 구성요소를 연결해 정상·오류·복구 시나리오를 검증한다.
- 실폰·실차 테스트, 외부 서버 배포, 스토어 제출은 이후 단계로 남긴다.
- 외부 계정 가입, 유료 서비스, 사용자 소유 인증정보를 필수 의존성으로 만들지 않는다.

**아래 필수 성공 기준이 모두 PASS이고 검증 증거가 있어야 이번 범위의 완료로 인정한다.** 빌드 성공, 화면 목업, 테스트용 보상 주입만으로 완료를 선언하지 않는다.

### 제품 범위

| 항목 | 구현 범위 |
|---|---|
| 세계관 | 여행가방 안에 사는 길콩이들이 여행 재료로 마을을 만드는 설정 |
| 주민 | 보따·토담·새미 3명, 각각 다른 외형·대사·생활 행동 |
| 마을 | 실제 3D 공간, 카메라 회전·확대·이동, 격자 배치 |
| 콘텐츠 | 건물 3종, 가구·장식 24종, 기본 재료 4종, 의뢰 14개 |
| 진행 | 7일 분량의 진행 곡선, 주민 초대와 마을 확장 |
| 생활감 | 걷기·대기·가구 사용, 제작과 입주 연출 |
| 오프라인 모바일 | 저장된 마을 감상, 배치 미리보기와 초안 저장 |
| 제외 | 전투, 거래, 친구 방문, 결제, iOS, 무제한 오픈월드 |

3D 확장성은 데이터로 주민·가구·구역을 추가하는 구조로 확보한다. 첫 버전의 콘텐츠 범위는 위 수량으로 고정한다.

## 2. 기술스택과 Pleos 연동

### 프로젝트 구조와 기술 선택

신규 앱은 `apps/lets-pleo/` 아래 독립 프로젝트로 구성한다. 기존 앱과 공용 빌드 설정은 변경하지 않는다.

| 구성요소 | 선택 기술 | 역할 |
|---|---|---|
| 차량 앱 | Kotlin, Jetpack Compose, Coroutines, Room | 탐험 시작, 차량 신호 구독, 로컬 기록, 보상 요약 |
| 모바일 앱 | Godot 4.7.2 Standard, typed GDScript, Compatibility renderer | 3D 마을과 게임 UI, 캐릭터 행동, 제작·배치 |
| 서버 | Node.js 22, TypeScript, Fastify | 계정 연결, 주행 검증, 보상·제작·진행 처리 |
| DB | SQLite, 트랜잭션과 마이그레이션 | 계정·보상 원장·인벤토리·마을 영속화 |
| 통신 | HTTP JSON, OpenAPI 계약 | 차량·모바일·서버 간 데이터 교환 |
| 에셋 | 자체 제작 저폴리곤 모델, 재사용 가능한 재질·애니메이션 | 외부 유료 에셋 없이 일관된 시각 디자인 |
| 검증 | JVM 테스트, 서버 통합 테스트, Godot headless 테스트, Android UI 테스트 | 규칙·API·실제 APK·연동 검증 |

차량 빌드는 기존 프로젝트와 동일한 JDK 17, Gradle 8.11.1, AGP 8.10.1, Kotlin 2.2.21, compileSdk 35, targetSdk 34, minSdk 28을 기준으로 시작한다. 모바일 Android 빌드는 Godot 공식 export template의 도구 조합을 따른다. 두 빌드의 Gradle 설정을 억지로 통일하지 않는다.

Godot는 공식 배포가 확인된 4.7.2와 동일 버전 export template을 고정한다. Android export에는 공식 안내의 JDK 17을 사용한다. 추가 라이브러리는 초기 빌드 검증 시 정확한 버전과 잠금 파일을 기록한다. [Godot 공식 배포 목록](https://godotengine.org/download/archive/), [Android export 문서](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_android.html)

### 사용할 차량 기능

| 기능 | API·SDK | 구현 목적 및 제한 |
|---|---|---|
| 차량 위치 | `ai.pleos.playground:FusedLocation:1.1.3` | 여행 위치와 풍경 테마 판정 |
| 위치 지원 확인 | `isSupported()` | 미지원 환경을 실제 수집 상태로 표시하지 않음 |
| 위치 생명주기 | 초기화·콜백 등록·해제·release | 연결 복구와 중복 구독 방지 |
| 속도·기어 | AAOS `CarPropertyManager`의 `PERF_VEHICLE_SPEED`, `GEAR_SELECTION` | 이동 구간과 주차 판정 |
| 차량 UX 제한 | `CarUxRestrictionsManager` | 주행·제한 상태에서 게임 조작 차단 |
| 화면 밖 수집 | 사용자 시작 기반 foreground service | 앱 화면을 벗어난 동안 탐험 유지 |

FusedLocation의 공개 권한은 `pleos.car.permission.FUSED_LOCATION`이다. 속도·기어 읽기는 Android 공식 문서의 `Car.PERMISSION_SPEED`, `Car.PERMISSION_POWERTRAIN`을 기준으로 선언하고, 실제 에뮬레이터의 지원·권한 상태를 검증한다. [Pleos 위치 SDK](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/intro), [공식 의존성](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/project-setup), [AAOS 차량 속성](https://developer.android.google.cn/reference/android/car/VehiclePropertyIds)

별도 Pleos Vehicle SDK, NaviHelper, STT, TTS, Gleo는 이번 기능에 필수적이지 않아 추가하지 않는다. 차량 제어 API는 사용하지 않는다.

Android는 백그라운드 서비스 시작을 제한하므로 **정차 상태의 화면에서 사용자가 탐험을 시작하는 방식**으로 구현한다. location foreground service에 필요한 Android 권한·서비스 선언과 Pleos 위치 권한의 실제 조합은 첫 기술 검증 단계에서 확인한다. 서비스가 유지되지 않는다면 핵심 미완료로 처리한다. [Android 백그라운드 시작 제한](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start?authuser=2)

### 초기 기술 검증을 먼저 하는 이유

`pleos-app-init`의 공식 API 확인 → 독립 앱 골격 → 빌드 검증 순서를 적용한다. 이후 게임 제품 구현으로 확장한다.

초기 단계에서 다음 네 가지를 실제로 확인한다.

1. Pleos 위치·속도·기어·UX 제한 신호 수신.
2. 다른 앱 화면으로 전환한 뒤에도 수집 유지.
3. Godot의 3D Android APK가 모바일 에뮬레이터에서 렌더링.
4. 두 에뮬레이터와 로컬 서버의 양방향 연결.

미지원 API를 가짜 구현으로 대체해 이 단계를 통과시키지 않는다.

## 3. 구현할 동작과 데이터 흐름

### 차량 탐험

상태는 `대기 → 탐험 준비 → 수집 중 → 일시 중단/종료 → 동기화 대기 → 반영 완료`로 관리한다.

- 탐험 시작은 기어 P, 정지, UX 제한 해제 상태에서만 허용한다.
- 이동 시간은 유효한 속도 신호에서 절댓값 1m/s 이상인 구간만 누적한다.
- 속도 신호가 5초 이상 끊기면 그 이후 구간은 누적하지 않는다.
- 기어 P와 정지 상태가 30초 유지되면 여행을 종료한다.
- 신호대기와 정체를 여행 종료로 처리하지 않는다.
- UX 제한 또는 차량 상태 불명 시 보상 개봉·설정·게임 조작을 잠근다. 속도 0만으로 잠금을 풀지 않는다.
- 신호가 끊긴 구간을 추정해서 보상하지 않는다.
- 강제 종료·재부팅 뒤에는 자동 수집을 보장하지 않는다. 기존 기록을 복구하고 다음 정차 시 재시작을 안내한다.

### 보상과 게임 경제

초기 규칙은 버전이 있는 공통 콘텐츠 데이터로 관리한다.

- 2026-11-15 사용자 요청 반영: 새 차량 클라이언트는 유효 이동 15초마다 서버에 적립 체크포인트를 보낸다. 나무는 15초당 2개, 돌은 1개, 천·씨앗은 30초당 1개씩 누적한다.
- 주행 화면은 서버가 적립한 수량만 표시한다. 정지·속도 신호 누락 구간은 이동 시간에 더하지 않으며, 오프라인에는 마지막 확인 수량을 유지한다.
- 도착 시 같은 적립 내역을 확정하고 모바일 수령을 허용한다. 수령 전에 인벤토리에 재료를 중복 반영하지 않는다.
- 일일 상한은 나무 12·돌 9·천 6·씨앗 3이다. 새 적립은 여행 시작일의 Asia/Seoul 날짜에 귀속하고, 기존 방식으로 받은 당일 보상도 상한에서 차감한다.
- 기존 5분/15분 기본·추가 보따리는 구형 클라이언트 호환 규칙으로만 유지한다. 실시간 적립을 시작한 계정의 후속 여행에는 새 규칙을 적용한다.
- 더 오래·빠르게 운전해도 일일 보상 상한을 넘지 않는다.
- 출발·종료 반복, 중복 업로드, 여러 차량 연결로 상한을 늘릴 수 없다.
- 튜토리얼 재료로 첫 주행 전에도 벤치를 제작·배치할 수 있다.
- 운전하지 않는 날에는 주민 의뢰와 정원 수확으로 기본 제작을 진행한다.
- 제작은 즉시 완료하며, 출석 누락·미접속에 따른 자산 손실은 없다.

풍경 테마는 도시·숲·바다 3종으로 만든다. 검증 가능한 위치 영역을 등록한 카탈로그로 판정하고, 등록되지 않은 지역은 일반 여행으로 표시한다. 첫 카탈로그는 테마별 2개 영역과 근거를 포함한다. 마지막 유효 위치가 등록 영역 안에 있을 때 해당 풍경 조각을 하루 최대 1개 지급한다. 위치 정보가 없으면 기본 보상만 지급한다.

풍경 조각은 외형 제작법 해금에 사용하며, 주민 의뢰에서도 얻을 수 있게 한다. 특정 지역 방문이 마을 성장의 필수 조건이 되지 않게 한다.

### 3D 마을과 콘텐츠

- 세로 화면, 360도 수평 회전, 제한된 높이 각도, 확대·축소·이동을 지원한다.
- 초기 12×12 격자에서 16×16, 20×20으로 확장한다.
- 가구 이동·90도 회전·보관·재배치를 지원한다.
- 영역 밖 배치, 겹침, 건물 출입구와 주민 접근 지점 봉쇄를 막는다.
- 주민은 격자 경로 탐색으로 이동하고 가구별 사용 지점을 예약한다.
- 가구 이동 중에는 해당 사용 동작을 해제하고 다시 경로를 계산한다.
- 주민마다 대기·걷기·고유 생활 행동을 구현하고, 공통으로 앉기를 지원한다.
- 작업장·주민 집·찻집을 만들고, 가구·장식 24종은 색상 변형을 제외한 서로 다른 모델로 센다.
- 14개 의뢰를 주민 초대·제작·배치·정원·마을 확장으로 연결한다.
- 크림·살구·세이지 색상, 무광 재질, 보자기·종이표·여행가방 형태를 공통 디자인으로 사용한다.
- 주민별 최소 12개 대사와 반복 완화 규칙을 제공한다.
- 의뢰 판정은 장식 태그와 실제 배치 상태로 수행하며, 가구를 삭제해 보상을 반복 수령할 수 없게 한다.

### 계정 연결과 서버 책임

모바일 첫 실행에서 게스트 계정을 생성하고, 일회용 연결 코드를 차량에 입력해 같은 마을을 연결한다. 이메일·OAuth는 이번 범위에 포함하지 않는다.

| 인터페이스 | 책임 |
|---|---|
| 게스트 세션·기기 연결·연결 해제 | 기기 인증과 계정 소유권 |
| 여행 제출 | 유효 기록 저장, 중복·겹침 제거 |
| 보상 수령 | 보따리 상태와 재료 지급을 하나의 트랜잭션으로 처리 |
| 게임 상태 조회 | 인벤토리·마을·주민·의뢰의 최신 상태 반환 |
| 제작 명령 | 서버의 레시피로 비용 검증·재료 차감·아이템 생성 |
| 배치 명령 | 소유권·좌표·충돌·마을 버전 검사 |
| 의뢰 완료 | 조건 검증과 1회 보상 |
| 콘텐츠 조회 | 레시피·주민·의뢰·테마 버전 전달 |

주요 데이터 타입은 `TripSummary`, `RewardGrant`, `Inventory`, `VillageSnapshot`, `Placement`, `ResidentProgress`, `QuestProgress`로 정의한다.

- 변경 명령은 고유 요청 ID를 사용한다.
- 재료 증감과 보상 여부는 서버만 확정한다.
- 배치는 마을 버전을 비교해 오래된 수정 요청을 거절한다.
- 모바일은 포그라운드 복귀 시와 변경 명령 완료 후 상태를 갱신한다.
- 차량의 미전송 여행은 Room에 저장하고 재연결 시 재전송한다.
- 모바일 오프라인 배치안은 초안으로만 저장하며 재연결 후 재검증한다.
- 원시 이동 경로는 서버에 저장하지 않는다. 차량에서 집계한 이동 시간·테마·기록 ID를 전송한다.
- 토큰은 로그에 남기지 않고 Android Keystore를 사용하는 보관 계층으로 저장한다.
- 로컬 개발용 HTTP 허용은 개발 빌드에만 적용한다.

|---|---|---|
| 0. 기반 검증 | 스킬 기반 초기세팅, SDK 권한, 화면 밖 수집, Godot APK, 로컬 통신 | A01~A06 및 B01~B03의 기술 경로 확인 |

### 실패하면 계속 개발하는 규칙

각 기준에 다음을 기록한다.

`ID / 상태 / 검증 명령 / 기대 결과 / 실제 결과 / 증거 경로 / 빌드 해시 / 결함`

상태는 `NOT_RUN`, `PASS`, `FAIL`, `BLOCKED`만 사용한다.

- `FAIL`: 원인을 수정하고 해당 테스트 및 영향을 받는 회귀 테스트를 다시 실행한다.
- `NOT_RUN`: 구현 여부와 관계없이 미완료다.
- `BLOCKED`: SDK·환경·권한 등 외부 제약의 근거를 기록한다. PASS나 범위 제외로 자동 변경하지 않는다.
- 실패를 없애려고 임계값을 낮추거나 필수 기능을 조용히 제거하지 않는다.
- 제품 변경 뒤에는 기존 증거의 유효성을 확인하고 영향을 받는 항목을 재검증한다.
- 마지막 후보 빌드에서 필수 테스트와 전체 통합 경로를 다시 통과해야 한다.

### 최종 인계물

- 차량 APK와 Android 모바일 APK.
- 서버 실행 패키지와 DB 마이그레이션·백업·복원 도구.
- 로컬 서버와 두 에뮬레이터의 실행·검증 스크립트.
- 전체 성공 기준 보고서와 항목별 로그·스크린샷·영상.
- API 계약, 콘텐츠 목록, 도구·SDK 버전, 재현 명령.
- 이후 실폰 연결 방법과 아직 실기기에서 검증하지 않은 항목.

최종 판정은 **“렛츠 플레오의 에뮬레이터 기반 개발 완료”**로 명시한다. 실폰·실차·스토어 검증은 별도 상태로 남기되, 이번 범위의 미구현이나 실패를 그 단계로 넘기지 않는다.
