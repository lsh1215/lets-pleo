서버 테스트 14개, TypeScript 빌드, Godot 스크립트 검사와 Android APK 내보내기가 통과했다. 최신 로컬 개발 서버를 기존 DB로 재시작했다. ## 차량 AVD 구성 복구

전용 LetsPleoCar가 320×640 세로 화면, 약 2.5GB 메모리로 실행되는 것을 확인했다. 설치된 Pleos devices.xml과 공식 가이드의 2560×1440 가로 화면·4GB·콜드 부팅 설정에 맞춰 전용 AVD만 수정했다. [변경 전](../verification/20261115/car-avd-before.ini), [변경 후](../verification/20261115/car-avd-corrected.ini). host GPU로 실행해 최신 차량 APK가 1.928초 안에 표시됐고 FusedLocation·AAOS 속도·기어 구독도 확인했다. A03을 PASS, B03을 재시험 대상으로 갱신했다.

전용 콘솔은 18088→5580:8088로 포워딩했다. 공식 콘솔 페이지가 사용하는 browser/session 갱신을 포함한 30분 주행 스크립트를 실행한다. 첫 시도는 세션 미갱신으로 503 종료됐으며 유효 시험으로 세지 않는다. 실제 완료 여부는 car-background-30min-run.txt와 수집 로그를 확인해야 한다. 다른 AVD와 다른 포트 포워딩은 변경하지 않았다.

## 성능 측정과 디스크 오류 복구

주민 3명·배치물 100개의 별도 APK를 600초 실행했다. 기존 SwiftShader(소프트웨어 렌더링) 환경에서는 4,303프레임, p95 322.339ms로 실패했다. [결과](../verification/20261115/mobile-perf-swiftshader-result.json). 전용 모바일 AVD만 host GPU, 412×915로 수정했다. 실제 Apple M2 Pro 렌더러를 확인했다. 시작 시간은 단순 첫 픽셀에 더해 제작 탭의 응답까지 측정했으며 8회 6.920–10.600초 이후 9회째 측정이 중단돼 완료된 10회 결과로 세지 않는다.

API 34·35 이미지를 별도 SDK 폴더에 풀던 중 디스크가 부족해 AVD 두 개가 자동 정지됐다. 내려받던 불완전한 폴더 6.9GB만 제거하고 전용 AVD의 `avd start`로 재개했다. 기존 사용자 파일·다른 AVD는 정리하지 않았다. 서버 SQLite 무결성은 정상이다. 30분 주행 시험은 1,679.6초 뒤 콘솔 timeout으로 끝나 실패로 기록했다. 복구 후 P/정지로 정상 종료해 1,685초 여행 1건이 서버에 동기화된 것을 확인했다. [실행 실패](../verification/20261115/car-background-30min-run.txt), [수집·복구·동기화 로그](../verification/20261115/car-background-interrupted-signals.txt). 30분 시험 통과로 인정하지 않는다.

대용량 SDK 다운로드는 장시간 시험과 함께 실행하지 않는다. 현재 GPU 환경의 10분 측정은 별도로 다시 시작했고 완료 결과를 확인해야 한다.

## 주행 제한과 강제 종료 복구 확인

새 차량 APK에서 P/정지의 실제 시작, 세 가지 제한 상태의 시작 차단, UX 제한 후 348.1ms 이내 버튼 숨김, 실제 위치·속도·기어·UX 콜백을 확인해 B01/B02/B05를 PASS로 갱신했다. [시나리오 결과](../verification/20261115/car-control-scenarios.json).

현재 전용 차량에서 [20회 화면 재진입 후 2시간 배경 수집](../verification/20261115/drive-endurance-2h.py)을 실행 중이다. `car-endurance-2h-run.txt`의 `complete`와 서버 저장·중복 여부까지 확인하기 전에는 완료로 판정하지 않는다. 시험 도중 차량 APK 재설치·앱 종료·콘솔 속도 변경을 하지 않는다.

### 22:22 — 30분 배경 수집 통과 및 모바일 내구성 시작

설정 앱 전면에서 30분 이상 실제 SDK 콜백과 이동 시간 1,875초가 유지돼 B03을 PASS로 갱신했다. B04는 계획서가 요구한 상태 전이 테스트 5개 실행 결과를 확인해 PASS로 정리했다. 현재 33 PASS / 3 FAIL / 15 NOT_RUN. 차량 2시간 시험은 계속 진행 중이며 종료·업로드 결과를 아직 판정하지 않는다.

### 사용자 범위 변경 — 제품 전체 검증에서 데모 준비로

사용자가 “2시간 차량 수집 시험은 너무 길어 … 데모만 나올 정도”라고 요청했다. 이에 차량·모바일 장시간 시험을 SIGINT로 의도적으로 중단했다. 차량 종료 처리에서 P/정지로 전환하고 이동 3,233초를 정상 저장·서버 업로드했다. 2시간/1시간 기준을 통과했다고 기록하지 않는다. 추가 API 35 부팅·검증, 새 계정 3회 통합·30분 오프라인 시험은 이번 데모 범위에서 진행하지 않는다.

기존 전용 차량 계정의 모바일 로그인만 로컬에서 복원했다. 변경 전 모바일 세션과 DB를 .runtime에 백업했고 재료·주행 기록은 수정하지 않았다. 기존 재료로 정상 제작/배치 API를 통해 주민 집·찻집을 더해 9개 배치물·3주민 시연 마을을 준비했다. 남은 실제 여행 보상 1건은 UI 시연에 사용한다. 이 계정 복원을 새 계정 3회 E01 통과 증거로 사용하지 않는다.


### 데모 준비 완료

제품 APK에서 남아 있던 실제 여행 보상 수령→꽃 화단 제작→배치를 확인하고 40.039초 H.264 영상으로 저장했다. 현재 전용 모바일은 배치물 10개·주민 3명의 마을, 전용 차량은 정차 시작 화면이다. 정상 제작/배치 API와 실제 터치만 사용했으며 재료 수량이나 보상 원장을 직접 늘리지 않았다. 별도 콘텐츠 시험 서버는 종료했다. 제품 서버와 두 전용 AVD만 데모용으로 유지한다. 이번 사용자 지정 데모 범위는 완료했으며 전체 51개 기준은 38 PASS / 2 FAIL / 11 NOT_RUN 그대로다. 실행 안내는 docs/demo-guide.md에 기록했다.


### 차량 → 마을 흐름으로 데모 수정

사용자가 모바일 화면 소개보다 “주행으로 얻은 것을 나중에 게임에서 쓰는” 연결을 요청했다. 차량 제한 화면에 실제 이동 기록 누적을 표시하고, 정차 종료 후 로컬 도착 영수증·서버 전달 상태를 추가했다. 서버 상태에 최근 실제 여행과 보상 재료를 노출하고, 모바일에 도착 선물·받을 재료·해당 재료로 만들 수 있는 가구 추천·제작 바로가기를 넣었다. 배치 성공 시 새 물체에 짧은 등장 연출을 적용했다.

기존 앱 초기화는 자동 승인 검토에서 데이터 손실 우려로 거절됐다. 삭제를 실행하지 않고 별도 앱 ID의 차량·모바일 데모를 설치해 새 게스트를 정상 코드 연결했다. 기존 제품 데이터와 다른 세션의 에뮬레이터는 유지했다. 모바일 데모의 main/models/residents/scene이 제품과 동일함을 대조했다.

전용 LetsPleoCar에서 36km/h·D 입력을 약 320초 유지하고 P·정지로 끝냈다. 실제 SDK가 이동 319초를 기록했고 서버에 여행 1건·기본 꾸러미 1개가 생겼다. Console 오류는 0건이었다. 모바일은 시작 재료로 벤치만 만들어 재료가 0인 상태였으며, 실제 UI에서 여행 보상 8/6/4/2를 수령하고 꽃 화단 제작·배치 → q01/q02 보상 → 토담 초대까지 통과했다. 최종 배치물은 벤치·화단 2개, 주민은 보따·토담 2명이다. 재료 직접 주입이나 시계 가속은 사용하지 않았다. 위치 테마는 이번 시연에서 null이며, 기본 재료 연결의 증거로만 사용한다.

증거: journey-drive-result.json, journey-mobile-result.json, journey-source-equivalence.json, 차량·모바일 원본 녹화 및 lets-pleo-vehicle-to-village-demo.mp4. 서버 테스트 15개·모바일 UI 계약 6개·차량 JVM 테스트 및 APK 빌드·모바일 export 통과. 이 단일 데모를 전체 51개 또는 3회 연속 통합 기준 완료로 계산하지 않는다.


### 차량 재료 수집 UI와 도착 영수증

사용자 요청에 따라 차량 주행 화면을 나무·돌·천·씨앗 아이콘과 여행 가방 중심으로 바꿨다. 자동 수집 상태를 보여주고 시간은 보조로 표시한다. 다른 앱 소스의 글자 크기를 대조해 본문 24–28sp, 제목 36–40sp, 주요 버튼 28sp·최소 76dp를 사용했다. 주행 중 클릭 대상은 0개이며 획득 팝업·점멸·수량 추정은 없다.

서버에 trip_receipts를 추가해 여행으로 새로 발급된 재료와 풍경 조각을 같은 DB 트랜잭션에 저장한다. 차량은 업로드 후 계정 범위를 확인하는 receipt API로 읽고 로컬에 저장한 다음 전송 큐를 지운다. 재전송·모바일 선행 수령에도 같은 결과가 유지된다. 이전 여행의 미보관 영수증, 전송 대기, 신규 재료 0개는 구분해 표시한다.

서버 16개 테스트·차량 9개 JVM 테스트 및 debug/demo APK 빌드 통과. 전용 LetsPleoCar의 demo 패키지만 데이터 보존 업데이트했다. 35초 실제 SDK 수집→자동 주차 종료→서버 영수증 저장→차량 확정 수량 표시까지 확인했다. 기존 기본 보상을 이미 받은 계정의 짧은 주행이므로 신규 재료는 모두 0이며, 서버·차량 영수증이 일치한다. 양수 수량(8/6/4/2)과 풍경 조각 UI는 예시 데이터임을 명시한 demo 전용 미리보기에서 확인했다. 제품 debug manifest에는 미리보기 Activity가 없다.

증거는 verification/20261115/materials/ 아래 car-build.txt, server-tests.txt, smoke-result.json, collecting-live.png, arrival-live.png, arrival-preview.png 및 상태별 XML이다. 검증 도중 미리보기 Activity가 이전 Intent를 재사용해 -S로 수정했고, run-as 인자 순서 문제는 완료된 주행을 반복하지 않고 저장된 영수증을 다시 읽어 확인했다. 기존 데이터와 다른 세션의 에뮬레이터는 변경하지 않았다. 장시간 검증이나 전체 51개 완료를 주장하지 않는다.


### 주행 중 실제 재료 적립과 모바일 사용 데모

사용자가 정적 그림이 아니라 주행 중 실제 재료가 쌓이는 흐름을 요청했다. 차량은 유효 이동 15초마다 수집 체크포인트를 전송하고 서버가 적립한 수량을 표시한다. collections 원장에 계정·여행·시작일·이동 시간·누적 재료·종료·수령 상태를 저장했다. 도착 전에는 모바일 수령을 차단하고, 도착 시 같은 원장을 확정한다. 기존 당일 보상까지 포함해 12/9/6/3 일일 상한을 적용한다. 5분/15분 규칙은 구형 클라이언트 호환용으로만 남겼으며 새 클라이언트는 실제로 점진 적립한다. 화면 숫자만 흉내 내는 방식이 아니다.

서버 18개 테스트와 차량 JVM 9개 테스트, debug/demo 빌드 통과. 반복 체크포인트·역순 재전송·조기 수령 차단·도착 수량 일치·중복 수령 방지·상한·오프라인 최종 제출·계정 격리·겹침 거절을 서버 테스트로 확인했다. 전용 LetsPleoCar에서 실제 이동 68초로 0/0/0/0 → 2/1/0/0 → 4/3/2/1 증가를 촬영했다. D/속도 0에서 10초 이상 동일 수량을 유지했고 P/정지 뒤 같은 4/3/2/1을 확정했다. 이 계정은 기존 8/6/4/2 보상이 있어 남은 일일 상한까지 적립했다.

모바일 실제 UI에서 동일 여행 ID의 보상을 수령해 인벤토리 증가량 4/3/2/1을 대조했다. 추천된 여행 벤치를 제작·배치했고 실제 재료 소비 4/1/0/0 및 신규 배치물 1개를 확인했다. 시계·인벤토리 주입 없이 전용 데모 계정의 기존 데이터를 유지했다. 원본 주행·모바일 영상과 편집한 89초 영상을 live-collection/에 보관했다. 전체 영상 디코딩과 주행/최종 마을 프레임을 검사했다. 다른 세션의 에뮬레이터는 조작하지 않았다. 전체 51개 제품 판정과 장시간 복구 검증은 후속으로 유지한다.
